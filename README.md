# dekopon-provider-chat

A Wasm provider for explicit, broker-scoped text history reads. It does not change automatic platform recall. Its separate `chat.slack.history.read` and `chat.discord.history.read` capabilities serve `chat slack get last N` and `chat discord get last N`, where `N` is an integer from 1 to 100. `chat send` and arbitrary channels, thread IDs, workspace IDs and URLs are not accepted. The provider does not expose file bytes or post messages.

An authorized call emits one JSON object with `messages` (oldest first) and `truncated` (true only when older messages were seen and omitted from the returned window). Each message has `id`, raw platform `author`, `time`, `text` and `assets`; each asset has `id`, `name`, `mime`, `size` (null when absent) and `available:false`. File references are descriptive only; there is no asset-import capability. Empty authorized history returns `{"messages":[],"truncated":false}`. Permission, throttling, unavailable history, malformed data and failed pages return nonzero errors, not empty success. Decoded response bytes are bounded by the broker grant (`maxResponseBytes: 524288` in the offline fixture), not a guest cap; a too-large response asks for fewer messages. At most two pages are read.

The provider sends GET `https://slack.com/api/conversations.replies?limit=L` (and, on a second page, `cursor`), where `L = min(200, max(20, 4 × N))` on both requests. Smaller N produces a smaller request size once above the minimum, so retrying with fewer messages can fit the broker's decoded-byte grant. It retains the newest N distinct messages seen across those pages. Slack pages forward from the thread root: if a thread runs beyond two pages of size L, the provider cannot reach its tail, so `last N` means the newest N reachable within the two-request budget, not necessarily the newest in the entire thread. **It does not send `channel` or `ts`.** The owner must attach one broker request template pinning `channel: conversation.id` and `ts: conversation.thread` to the attested `ChatScopeClaim`, allowing only `limit` and `cursor`. [The offline fixture](tests/fixtures/broker.yaml) shows the required host, request budget, method and template. Without a claim/thread slot, broker invocation refuses before HTTP; a Classic-mode DM without a thread cannot use this capability. Classic-mode Slack channel roots and Agent-mode DMs and channel roots carrying their own root thread slot can read only that root via replies, never `conversations.history`. Discord sends `https://discord.com/api/v10/channels/{conversation.apiChannel}/messages?limit=N+1` (at most 50 per page, with `before` for a second page) to observe whether an older message is omitted; a full final page without an observed extra message alone does not establish truncation. Its single path template replaces that slot with the attested channel or thread ID; a foreign channel denies before DNS. Discord attachments remain descriptive only. Discord may return HTTP 200 with an empty array when Read Message History permission is absent; this provider cannot distinguish that response from genuinely empty authorized history. A provider manifest alone is *not* authorization: the broker's credential, constraint set and Cedar grant remain separate owner actions. The example credential in tests is synthetic and must never be deployed. Fixture transports `slack.test` and `discord.test` are offline examples, not live `dekoponville` or `discord-dekopon` grant values.

To validate locally, use the [agent guide](AGENTS.md) gates and `python3 tests/verify_broker.py` with brokerd 0.47.0 on `PATH` or `DEKOPON_BROKERD=<path>`. That script uses private temporary files and terminates its own test broker; it never contacts either platform. `dekopon-brokerd check` intentionally does not read credentials: it checks static templates/metadata and warns that credential binding is verified at boot. Boot rejects credential/host mismatches.
